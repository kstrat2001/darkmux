Crawl a codebase against your rules, and route what it finds

Beta. The crawl mission and hooks shipped in 3.4.0 as a public beta: the pieces on this page run and are exercised on darkmux's own code every day, but the mission inputs and the hook record shapes may still change between minor releases without a deprecation period. Mechanical coverage accounting and typed hook kinds are not built yet.

A crawl (#1959) is a mission like any other: point it at real source trees, name the rules you want checked, and a local model reads bounded slices of code and reports findings through report_finding. Everything the crawl does streams as ordinary flow records, so the last piece is routing: hooks (#2093) match those records against operator rules and POST the matches to your own receiver — loopback on the same machine, or another machine on your own tailnet (#2135 option 2). No external tracker knows darkmux exists, and darkmux never leaves that boundary to reach one.

When you'd use this

This is the deep end of the guide. Use it when you want a standing, repeatable check — "does this codebase have swallowed errors, or doc comments the code no longer matches" — run by a local model against a workspace you name, with the findings routed somewhere you already look (an issue tracker, a Slack-posting script, your own dashboard) instead of read off the terminal by hand.

The two halves compose but ship independently: you can run a crawl and read its findings straight from the flow log with no hooks configured at all, or wire hooks to route any flow record (mission lifecycle, dispatch bookends, a specific tool call) with no crawl in the picture. This page walks both, in the order you'd actually set them up.

1. The workspace spec

A crawl's target is a workspace spec: a JSON document naming one or more source trees, what to include/exclude, and which rules to check. Save it anywhere and pass its path to --param workspace=. Here it is pointed at darkmux's own public repo — never point a workspace spec at engagement-private source, per darkmux's own no-public-repo-for-personal-engagements posture:

{
  "schema_version": "1.0",
  "name": "darkmux-self",
  "sources": [
    { "id": "darkmux", "git": "git@github.com:kstrat2001/darkmux.git", "ref": "main" }
  ],
  "include": ["**/*.ts", "**/*.tsx", "**/*.js", "**/*.mjs", "**/*.md"],
  "exclude": ["**/node_modules/**", "**/dist/**", "**/docs/demo/**", "**/target/**"],
  "edges": [],
  "rules": ["swallowed-error", "doc-contradicts-code"]
}
  • sources[]: each entry is either git (cloned once into ~/.darkmux/workspaces/<name>/tree and reused across launches at the same ref) or path (a local directory, used in place). ref names the branch/tag/sha to check out.
  • include/exclude: glob lists that narrow the file set every rule's applies_to further narrows per-rule.
  • edges: dependency edges between sources, consumed by edge-kind rules (see the built-in stale-consumer rule below). Empty here — this spec has one source.
  • rules: the rule ids to check, resolved the same way roles resolve: user tier (~/.darkmux/rules/) first, then the embedded built-ins.

Preview the plan with --dry-run

Before spending any model time, resolve the spec and see exactly what would run — file counts, unit counts, and a token estimate — with nothing minted and nothing dispatched:

darkmux mission launch crawl --param workspace=/path/to/darkmux-self.json --dry-run

Real output, captured against the spec above:

Each source row shows in_scope/out_of_scope file counts after include/exclude narrowing; each rule row shows how many units (one unit = one bounded dispatch's worth of work) it decomposed into, plus a rough token estimate so you can gauge cost before committing a single dispatch.

Discrepancy from what you might expect: workspace= takes a file PATH, not inline JSON.

Passing the spec's JSON text directly as the --param value fails: darkmux tries to open() the string you gave it as a filesystem path and reports No such file or directory, quoting the JSON back at you inside the error as if it had been read as a document, not a path — which reads as a parse failure on first glance but is actually a file-not-found on a path that happens to be a long JSON blob. Write the spec to a file and pass its path; that's the only form that resolves.

2. Rules: a template kind, like roles

A rule is a named, searchable property bound to files by glob — the same registry shape roles use (embedded built-ins, overridable at a user tier), and not crawl-specific: any role's mission can use the rules registry, the crawler is just its first consumer. darkmux ships three built-ins at templates/builtin/rules/:

RuleKindWhat it looks for
swallowed-errorsiteA catch/.catch(...)/void somePromise() site where the failure is neither rethrown, logged, nor checked by the caller.
doc-contradicts-codereadA doc comment or README claim the adjacent code visibly does not do.
stale-consumeredgeA consumer's pinned dependency range excludes a library version whose imported symbols changed shape.

The three kinds shape how a rule turns into work: site rules run a cheap mechanical prefilter (a regex) over the file set first, so the model only reads sites the prefilter flags, costing no tokens on files it never touches; read rules have no prefilter and ride the same read pass every other read rule shares, over whole files grouped up to chunk_tokens; edge rules fire on a dependency edge the workspace spec's own edges array declares. Here's the full shape of the swallowed-error rule, the site case:

{
  "id": "swallowed-error",
  "kind": "site",
  "title": "A failure is caught or discarded and nothing records that it happened",
  "applies_to": ["**/*.ts", "**/*.tsx", "**/*.js", "**/*.mjs", "**/*.cjs"],
  "exclude": ["**/node_modules/**", "**/dist/**", "**/build/**", "**/*.test.*", "**/*.spec.*"],
  "prefilter": ["\\bcatch\\s*(\\(|\\{)", "\\.catch\\s*\\(", "^\\s*void\\s+[A-Za-z_$][\\w$.]*\\s*\\("],
  "window": 30,
  "match": "The site is a `catch` clause, a `.catch(...)` handler, or a `void somePromise()` statement, AND the failure that reaches it is neither rethrown, nor returned as an error value the caller checks, nor logged, nor counted, nor recorded anywhere the surrounding lines show.",
  "no_match": "The handler rethrows or wraps and throws. The handler logs. A comment says why ignoring the failure is safe. Test code, generated code, or a `.d.ts`.",
  "evidence": "The `catch`/`.catch`/`void` line, copied verbatim. `line` is where it appears.",
  "why_hint": "Say what operation failed silently and what downstream code assumes about it."
}

match/no_match are the positive and negative criteria the model is given verbatim; evidence and why_hint shape what a reported finding must cite. Author your own at ~/.darkmux/rules/<id>.json — same shape, same registry, resolved ahead of the built-ins by id.

Rule problems surface in darkmux doctor

Doctor loads the whole registry (not just one workspace's resolved subset) and reports count plus provenance. On this machine, with no user-tier rules yet, that line reads:

✓ rules                  3 rule(s) loaded (3 built-in, no user tier)

A malformed user-tier file, an empty applies_to, or a site rule with no prefilter would surface here as a named warning rather than a silent skip or a hard failure at launch time.

3. Running a unit

Add --param limit=N to actually dispatch instead of previewing:

darkmux mission launch crawl --param workspace=/path/to/darkmux-self.json --param limit=1

Dropping --dry-run mints a real mission, clones (or reuses) the source tree, and dispatches one unit per selected plan row to a local model — the same internal-runtime container path darkmux dispatch uses. A crawl unit is a real dispatch and can run for minutes: this page does not run one live (another job was already running one while this page was written), instead reading and scrubbing the records of a completed crawl mission straight from ~/.darkmux/flows/<date>.jsonl.

The record sequence

Generic mission/dispatch bookends wrap the crawl-specific work, in this order for one unit:

mission start          # operator-tier: workspace, units_in_plan, units_selected, est_tokens
phase start
step start
dispatch start          # local-tier: role=crawler, the assembled prompt, the model
dispatch.turn / dispatch.tool / dispatch.reasoning   # the loop, repeated per turn
dispatch.rest           # only when runtime.turn_delay_ms is set — see the knobs table below
step complete            # findings, exclusions, wall_ms, rest_ms, per-unit token counts
dispatch complete        # wall_ms, rests, total_turns, total_tools, total_tokens
# ...repeated per selected unit...
mission close            # units_completed/errored/skipped, stopped_by, tokens_per_hour

4. Hooks: routing flow records to your own receiver

Hooks are darkmux's fourth FlowSink kind: match a flow record against operator-configured rules and POST a match verbatim to a receiver you run. Loopback, or your tailnet — nothing else. A rule's http target is accepted when it's loopback (127.0.0.1/[::1]/localhost) OR a genuine Tailscale address (an IPv4 in 100.64.0.0/10, or a hostname ending in .ts.net) — validate_hook_target_url refuses everything else, checked both when the rule loads and again at every POST. There's no config flag to flip: the URL itself is the decision (a loopback receiver, or a receiver on another machine in the SAME tailnet), and darkmux doctor/flow status show each rule's resolved target kind (loopback/tailnet) so the choice stays visible. darkmux never reaches an external tracker outside that boundary; a tailnet target still requires http:// (WireGuard already encrypts and authenticates the peer, so TLS on top buys nothing), and an external (non-tailnet) receiver is a later packet that will require https:// plus a mandatory signature.

The config block

config.hooks, same visible-defaults shape as redis/audit. This is the real block from a running machine (URLs are loopback, nothing else to scrub):

{
  "hooks": {
    "enabled": true,
    "rules": [
      { "match": { "action": "dispatch.tool", "payload.tool_name": "report_finding", "payload.ok": true },
        "http": "http://127.0.0.1:8790/events" },
      { "match": { "action": "step *" },
        "http": "http://127.0.0.1:8790/events" },
      { "match": { "action": "mission *" },
        "http": "http://127.0.0.1:8790/events" }
    ]
  }
}

Two fields the full schema also supports, outbox_dir and max_outbox_mb, are absent from this particular file — they're Option fields with defaults (~/.darkmux/hooks, 256 MiB) filled in at read time, and darkmux doctor/flow status below show the resolved values even though the file itself only sets enabled and rules.

The match vocabulary

A rule's match object ANDs together every key it names. Top-level fields: action, session_id, mission_id, machine_id, category, level. A glob suffix ("step *", "mission *") matches any action starting with that prefix. Past the top level, a "payload.<dotted.path>" key reaches into the record's own payload for an exact scalar match — the third rule above's payload.tool_name/payload.ok pair is how you subscribe to one specific tool call's outcome rather than an entire action glob. A key the payload doesn't carry never matches; there's no "absent means match" reading.

hook.fired / hook.failed

Every delivery attempt emits its own flow record — hook.fired on a 2xx, hook.failed once bounded retries give up. Real hook.fired record from the crawl mission above, showing the run's step start rule firing:

{"action":"hook.fired","source":"hook","payload":{"rule_index":1,
   "target_host":"127.0.0.1:8790","delivered_action":"step start","attempt":1}}

A 2xx response can still carry a per-record rejection: if the receiver's JSON body reports {"rejected": N}, that count rides on the same hook.fired record as payload.receiver_rejected — the delivery is still consumed either way (at-least-once), but a receiver quietly refusing records inside a 200 is never silent:

{"action":"hook.fired","source":"hook","payload":{"rule_index":0,
   "target_host":"127.0.0.1:8790","delivered_action":"dispatch.tool",
   "attempt":1,"receiver_rejected":1}}

hook.failed didn't fire in this environment's log — delivery has been succeeding — but it exists for the give-up path (a permanent 4xx/redirect, or retries exhausted against a down receiver) and carries the same rule_index/target_host shape plus the failure reason. Both records also carry delivery_id — the SAME id the delivery attempt carried on the wire (below), so a record here correlates directly with the HTTP request your receiver actually saw.

Delivery headers

Every delivery — loopback or tailnet — carries the same set of headers, whether or not the rule is signed:

HeaderValue
X-Darkmux-DeliveryA UUID-v4-shaped id, deterministically derived from the exact outbox line — every RETRY of the same undelivered line carries the SAME id (the "delivery attempt group"), and it's also stamped as delivery_id on the corresponding hook.fired/hook.failed record.
X-Darkmux-EventThe record's own action field (e.g. dispatch.tool, step start).
X-Darkmux-Machine-Id / X-Darkmux-Machine-UidThe machine that PRODUCED the record — from the record's own machine_id/machine_uid fields.
X-Darkmux-SenderTHIS host's own machine_id — the machine POSTing. Distinct from X-Darkmux-Machine-Id on purpose: a fleet hub relaying another machine's record would otherwise be indistinguishable from that record's origin.
X-Darkmux-TimestampUnix milliseconds at send time.
X-Darkmux-SignaturePresent ONLY when the rule names a signing_secret_keychain_item: sha256=<hex HMAC-SHA256> over the literal string "<timestamp>.<raw body bytes>", using the value of X-Darkmux-Timestamp as-is. Absent on an unsigned rule — never a placeholder or empty value.

The secret itself is never in config.json or a log — only the macOS Keychain item NAME is: signing_secret_keychain_item per rule, read via security find-generic-password -a $USER -s <item> -w at construction. Non-macOS (or a portable override on any platform): set DARKMUX_HOOK_SECRET_<rule-index> instead (e.g. DARKMUX_HOOK_SECRET_0 for rules[0]) — that env var wins over the Keychain item whenever it's set. Signing is optional inside a loopback receiver on the SAME machine; darkmux doctor warns when a TAILNET target has no secret configured (fine inside the tailnet, since WireGuard already authenticates the peer — but the receiver then has no way to attribute the record's sender beyond the body itself).

{
  "hooks": {
    "enabled": true,
    "rules": [
      { "match": { "action": "step *" },
        "http": "http://100.64.1.2:8790/events",
        "signing_secret_keychain_item": "darkmux-hook-crawl-tracker" }
    ]
  }
}

(Keychain item, on the sending machine: security add-generic-password -a $USER -s darkmux-hook-crawl-tracker -w, then paste the shared secret.)

darkmux flow drain

Flushes every rule's outbox synchronously instead of waiting for the background drainer's own cadence. With nothing pending, real output is a one-liner:

darkmux flow drain (all rules) — delivered: 0, failed: 0

--file <path> --to <url> drains a single stray outbox file whose owning rule was since removed or edited — darkmux doctor names any stray files it finds under the outbox dir.

A minimal receiver

You don't need the operator's own tracker to try this — any process that accepts a POST and returns 2xx works. Fifteen lines, tested against a real hook delivery while writing this page:

import http from "node:http";

http.createServer((req, res) => {
  if (req.method !== "POST") { res.writeHead(405).end(); return; }
  let body = "";
  req.on("data", (chunk) => { body += chunk; });
  req.on("end", () => {
    const record = JSON.parse(body);
    console.log(`[${record.action}] ${record.mission_id ?? record.session_id ?? ""}`);
    res.writeHead(200, { "Content-Type": "application/json" });
    res.end(JSON.stringify({ rejected: 0 }));
  });
}).listen(8790, "127.0.0.1", () => {
  console.log("listening on http://127.0.0.1:8790/events");
});

Run it (node receiver.mjs), point a hook rule's http at http://127.0.0.1:8790/events, and every matching flow record prints as it's delivered. The {"rejected": N} response body is optional — return a bare 200 and every delivery just reads as accepted.

Transforms: reshaping a record for someone else's API

A raw flow record is darkmux's own shape. A real external tracker — Jira, a ticketing API, anything you don't control — wants ITS shape. A transform is a jq filter, evaluated in-process (jaq, pure Rust, no C bindings, no subprocess) at DELIVERY time — record in, request body out. It's a pure function on purpose: no filesystem, no network, no Keychain access from inside the filter itself. Two independent knobs on a rule: transform (the shape) and the destination (http + headers, or file — below) — only the destination ever touches a credential.

transform is a NAME, resolved inside <outbox_dir>/adapters/ (normally ~/.darkmux/hooks/adapters/) — never a path. A bare filename only; /, \, .., or an absolute string are refused when the rule loads. Absent transform is today's behavior, byte-identical: the record delivered verbatim. The adapter's TEXT is read once at load time and cached — a hand-edited adapter file takes effect on the next config reload, not mid-run; doctor/flow status re-read + re-hash the file live, so a hot edit can show a different hash there than the one actually driving a running sink.

Reality check before the example: http's URL policy is UNCHANGED by this packet. validate_hook_target_url still accepts loopback or a genuine tailnet address ONLY, and still requires the literal http:// scheme — an https://your-site.atlassian.net/... target is refused at load, same as before, whole sink down if any rule names one. This packet adds headers (so a rule that already targets a receiver you can reach — loopback, or something on YOUR tailnet — can carry auth) and the file transport (so you can develop + verify an adapter's shape with zero network at all). Reaching a genuine external SaaS endpoint over real https is still refused, pending a separate later packet that pairs it with a MANDATORY signature. The example below targets a tracker reachable on your tailnet (a self-hosted Jira/OpenProject/whatever instance, or an echo receiver) — swap the host for your own tailnet address:

{ "match": { "action": "dispatch.tool", "payload.tool_name": "report_finding", "payload.ok": true },
  "http": "http://100.64.1.2:8080/rest/api/3/issue",
  "headers": {
    "Content-Type": "application/json",
    "Accept": "application/json",
    "Authorization": { "keychain_item": "darkmux-hook-jira" }
  },
  "transform": "jira-issue.jq" }

headers is a name -> value map: a plain string is sent as-is; {"keychain_item": "..."} resolves a macOS Keychain generic-password item at delivery time and sends ITS value — the item holds the COMPLETE header value (Basic <base64(email:api-token)>, Bearer <token>, whatever the receiver wants), never a raw token darkmux formats itself, so this stays scheme-agnostic. A Keychain-resolved value never appears in a flow record, a log line, doctor output, or a file-transport dump — those all print "<redacted>" instead. attribution_headers: false on a rule drops the X-Darkmux-* set entirely, for a receiver that rejects unknown headers — useful today on a self-hosted tailnet tracker; load-bearing once a real external target lands.

~/.darkmux/hooks/adapters/jira-issue.jq — ordinary jq, building Jira's nested fields shape:

{
  fields: {
    project: { key: "OPS" },
    summary: ("crawl finding: " + .payload.tool_name),
    description: {
      type: "doc", version: 1,
      content: [{ type: "paragraph",
                  content: [{ type: "text", text: (.payload.evidence // "") }] }]
    },
    issuetype: { name: "Bug" }
  }
}

A transform must produce EXACTLY ONE output that's either a JSON object (serialized compactly, becomes the request body) or a string (its raw bytes become the body — for a non-JSON receiver). Anything else — a jq syntax error, a runtime error (error("...")), a timeout, an oversize output, zero or more-than-one output values, or a bare number/array/null result — is a TERMINAL failure for that line: quarantined, hook.failed carries a bounded excerpt of the error, and the line is never retried (a bad adapter is a construction bug, not a transient one). Two bounds, both visible config.json knobs under hooks: jq_timeout_ms (default 5000 — wall-clock, compile + run) and jq_max_output_bytes (default 1048576 — the produced body's byte length).

Three testing tiers

  1. Adapter alone, no darkmux involved. Fixtures come free from the flow log: jq -c 'select(.payload.tool_name=="report_finding")' ~/.darkmux/flows/<date>.jsonl | head -1 | jq -f ~/.darkmux/hooks/adapters/jira-issue.jq. jaq isn't byte-for-byte jq on every edge — test with a real jq binary here, since that's the ground truth an adapter author reasons against.
  2. file transport — darkmux involved, no network. A rule names file instead of http (exactly one of the two; both or neither is refused at load): each matching delivery writes ONE JSON file into that directory — {delivery_id, target_would_be, headers, body}, secret header values redacted, file mode 0o600 — and emits hook.dry_run (informational) instead of hook.fired, advancing the cursor same as a real delivery. 
    { "match": { "action": "dispatch.tool", "payload.tool_name": "report_finding" },
  "file": "~/darkmux-hook-dryrun",
  "transform": "jira-issue.jq" }
  3. The full path, against a local echo receiver — the fifteen-line Node receiver above, or the real remote endpoint once you trust the shape.

darkmux doctor

A rule naming a transform gets an extra clause on its row: the adapter name, whether it exists + parses, and its BLAKE3 content hash (first 16 hex chars) — so a silently-edited adapter is visible without diffing the file by hand. A missing or unparseable adapter is a load-time refusal SCOPED TO THAT RULE — the rest of the sink (every other rule) keeps running, unlike a bad http URL, which still refuses the whole sink.

#0: payload.tool_name="report_finding" -> http://100.64.1.2:8080/rest/api/3/issue [tailnet, unsigned], transform: jira-issue.jq (sha256:a1b2c3d4e5f6a7b8) (undelivered: 0)

Honest limits

  • At-least-once is not idempotent. Jira's create-issue endpoint has no idempotency key — a lost response can duplicate an issue. The stable delivery_id can be written into a searchable custom field by the adapter itself, but true check-then-create needs a SECOND request (does this delivery_id already exist? if not, create) — that's a multi-request integration, which exceeds what a pure jq filter can do by design. It's the cmd transport's job (a later, separately-gated packet), not this one's.
  • jaq is not byte-for-byte jq on every edge case. Test adapters against jaq itself (tier 1 above uses the system jq as ground truth, but the actual delivery path runs jaq) if a filter leans on an obscure builtin.
  • Multi-request integrations exceed jq by design. A transform is record -> body, one function, one output — not a workflow.

5. The knobs

Names and defaults copied verbatim from docs/ENVIRONMENT.md:

Env varDefaultconfig.json fieldWhat it does
DARKMUX_TURN_DELAY_MS 0 runtime.turn_delay_ms Global inter-turn rest — the runtime sleeps this many milliseconds between turns only (never before the first, never after the last). Recorded as rest_ms/rests alongside an unchanged wall_ms. Clamped to at most half of DARKMUX_INACTIVITY_TIMEOUT_SECONDS, with a loud warning naming the clamp if it fires. Never applied to an agentic-remote dispatch.
DARKMUX_HOST_SAMPLER_INTERVAL_MS 5000 runtime.host_sampler_interval_ms The serve daemon's continuous host sampler cadence — CPU/memory/thermal/GPU read in-process from kernel counters, zero model work, zero process spawns. Measured mean cost ~9.7 ms per sample on an M5 Max. 0 disables it.
DARKMUX_HOOKS_ENABLED false hooks.enabled The whole-feature gate for hooks. No per-rule env override exists — a rule is a structured object an env var can't carry; this only turns the feature as a whole on/off.
DARKMUX_HOOKS_MAX_OUTBOX_MB 256 hooks.max_outbox_mb The hard cap, in MiB, on undelivered bytes a single rule's outbox may hold before further appends for that rule are dropped (counted, never silently lost). 0 disables the cap. Read once, live, at construction.
DARKMUX_HOOK_SECRET_<rule-index> unset — (a secret; never config.json) A rule's HMAC-SHA256 signing secret, verbatim — e.g. DARKMUX_HOOK_SECRET_0 for rules[0]. Wins over that rule's signing_secret_keychain_item whenever set, on every platform (the portable / non-macOS path). Never logged.
