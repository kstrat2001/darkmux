Bring your own bundler

The review funnel's built-in bundler (darkmux mission launch review) parses TypeScript only. The --bundler flag is the escape hatch: point it at any external command that emits the same frozen JSON contract, and that command stands in for the built-in one. This page documents the contract field by field and walks through one of the two shipped reference plugins.

Why this exists

darkmux's built-in bundler splits a diff into per-changed-function code bundles by parsing TypeScript: .ts/.tsx files, walking function boundaries, resolving callees and siblings against a repo-wide index. It has no notion of any other language. A diff that touches .rs, .py, .go, .sql, .css, Edge.js templates, or anything else the built-in bundler can't parse used to read as a bare "no bundles produced" outcome, indistinguishable from a genuine bundler bug.

--bundler fixes the ceiling, not the floor: instead of teaching the built-in bundler every language darkmux might ever review, any command that speaks the frozen contract can plug in. darkmux reviews its own (Rust) pull requests through exactly this mechanism; see the missions guide for how mission launch review fits into the wider agentic surface.

The contract

Invoked exactly as:

<cmd> --diff <file> [--worktree <dir>]
  • --diff <file>: a unified diff (as produced by git diff / gh pr diff). Always supplied.
  • --worktree <dir>: a local checkout to read full file contents from. Supplied when the review has one; omitted entirely when the source is a GitHub API fetch with no local checkout (darkmux's own self-review workflow runs this way). A bundler should still produce output from the diff's own hunk context alone when --worktree is absent, just without whole-file spans.

On success: exit 0 and print a BundleSet JSON document on stdout, {"bundles": [...]}. Each entry in bundles is one Bundle:

FieldTypeRequiredMeaning
idstringyes, non-emptyGroups a function's family-variant bundles. Convention: "<fn>@<path>"; a consumer should not assume that exact shape for a unit that isn't a named function (a template, say).
codearray of {path, start, end}yes, non-empty1-indexed, inclusive line spans the review pipeline resolves against the worktree.
factsarray of stringyes (may be empty)Mechanical, non-judgmental observations about the diff: counts, additions/removals, presence/absence checks. Never a ranked or interpreted finding.
fact_familystringyes, non-emptyNames which family facts belongs to. Both shipped reference plugins use "differential"; see honest limits below for what the other built-in families require.
manifestarray of stringoptional, default emptyExternal symbols the bundle's code references but doesn't define: other functions, included templates, whatever "external reference" means for the language.
truncatedbooloptional, default falseTrue when a code span shows less than the full extent of what it's pointing at (a windowed excerpt rather than the whole unit).

This JSON shape is frozen. manifest and truncated are additive: safe for an older consumer to ignore, never required for a minimal plugin to populate.

Loud failure, not a silent pass.

A non-zero exit, non-JSON stdout, a missing bundles field, a bundle missing a required field, or an empty bundles array (0 bundles) are all treated as errors the review surfaces, never a quiet no-op. If your plugin finds nothing reviewable in the diff, exit non-zero with a clear message on stderr rather than printing {"bundles": []}.

Worked example: darkmux-bundler-edge

Two reference plugins ship in the repo under plugins/: darkmux-bundler-rust (a standalone Cargo project that bundles .rs files, used by darkmux's own CI to review its own pull requests) and darkmux-bundler-edge (a single Python script for Edge.js templates). This walkthrough picks darkmux-bundler-edge: it's a single ~200-line file with zero dependencies, so the whole contract fits on one screen. The Rust plugin does the same job with more machinery (its own diff/scan/facts modules) because Rust source needs more structure to parse than a template language does.

Emit mechanical facts

All in the "differential" family: line/hunk counts; interpolation expressions ({{ expr }}) added or removed, with Edge comments ({{-- ... --}}) explicitly excluded since they're documentation, not template logic; directive line changes (@if/@each/@component/@include/...); class="..." attribute churn. Every fact is a mechanical count or presence check, never a judgment call.

Build the manifest and assemble the bundle

@include(...) and @!component(...) targets become the bundle's manifest entries, a template naming itself (say, inside a usage-example comment) is excluded since that's not an external reference. The main loop assembles one bundle per touched file and prints the whole set as a single line of JSON:

bundles = []
for path, hunks in sorted(files.items()):
    code, truncated, text = code_refs(path, hunks, args.worktree)
    template = Path(path).stem
    bundle = {
        "id": f"{template}@{path}",
        "code": code,
        "facts": facts_for(hunks),
        "fact_family": "differential",
    }
    manifest = manifest_for(text, hunks, template)
    if manifest:
        bundle["manifest"] = manifest
    if truncated:
        bundle["truncated"] = True
    bundles.append(bundle)

print(json.dumps({"bundles": bundles}))
return 0

And the loud-failure half: when the diff has no .edge hunks at all, it prints a clear message to stderr and exits 1 rather than emitting an empty bundle set:

if not files:
    print(
        "darkmux-bundler-edge: no .edge files with reviewable hunks in this diff — nothing "
        "to bundle. (If this diff touches TypeScript, the built-in bundler is the right "
        "tool; this plugin only handles Edge templates.)",
        file=sys.stderr,
    )
    return 1

That's the whole contract satisfied: read --diff (and optionally --worktree), either print a non-empty {"bundles": [...]} and exit 0, or fail loud on stderr and exit non-zero.

Wiring it in

Name the command on the bundler input when launching a review:

darkmux mission launch review --param bundler=darkmux-bundler-edge

Any command on PATH, or a full path, works. This is the same public bundler input a third-party plugin author would use; there's no privileged internal seam darkmux's own tooling gets that a plugin author doesn't.

darkmux's own CI (.github/workflows/darkmux-review.yml) uses this exact seam to review darkmux's own Rust pull requests: it builds darkmux-bundler-rust from a trusted checkout of main as a standalone Cargo project, then passes its built path the same way:

cd plugins/darkmux-bundler-rust
cargo build --release --locked
# ... then, on the review launch:
darkmux mission launch review \
  --param bundler=/path/to/darkmux-bundler-rust \
  --param diff_file=pr.diff \
  --param github=owner/repo \
  --param head_sha=abc123

Without this, every self-review of darkmux's own Rust source produced 0 bundles: the built-in bundler simply can't read .rs. Point --bundler at whatever plugin matches your repo's language, and the review funnel runs the same bundle → probe → dedup → judge → verify → synthesis pipeline on top of it.

Honest limits

A custom bundler doesn't get everything the built-in one does for free:

  • Fact families. The built-in bundler computes three: param-flow, differential, and siblings. Both shipped reference plugins emit only differential; param-flow (a callee's signature vs. what the caller actually passes) and siblings (same-named functions elsewhere in the repo) both depend on machinery a plugin has to build itself if it wants them.
  • Callee/sibling resolution. The built-in bundler maintains a repo-wide function index and resolves each changed function's callees and siblings against it, so a bundle can carry a callee's real signature or point at a sibling implementation elsewhere in the codebase. That index is TypeScript-specific static analysis; an external bundler has no equivalent unless it builds one.
  • Per-file decline accounting. The built-in bundler records exactly why each declined file produced no bundle (non-code data, an over-size function, an unreadable file, and so on), which is what lets a genuinely empty diff read as an honest "nothing here" rather than an unexplained failure. An external bundler carries none of that bookkeeping, so a zero-bundle run from a --bundler plugin always reads as the unexplained "can't tell you why" case, not the neutral one.

None of this blocks a plugin from being useful. A bundler that only emits differential facts and good code spans still gives the review funnel real code to look at, which is the whole point: some signal in a language the built-in bundler can't touch beats no signal at all.
