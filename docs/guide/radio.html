radio: talk to the command registry

A conversational channel over darkmux's advertised commands. Instead of remembering that a review is darkmux mission launch review, you say what you want in plain text and a bounded routing dispatch picks one advertised command, or refuses rather than guess. A refusal isn't a dead end: the same text goes to a second, grounded seat that answers in prose instead.

The problem it solves

darkmux's command surface grows as you and your mission configs grow: built-ins like review, plus whatever procedural or agentic commands you've advertised yourself (see Task/Step graphs for how a mission config becomes a runnable command). Memorizing exact ids and flags doesn't scale, and it's the wrong layer to ask an operator to hold in their head at a terminal.

darkmux radio "<text>" takes one short message and maps it onto exactly one advertised command, or declines. It never invents a command, never chains commands, and never guesses when a message is ambiguous. Those are the two safety walls this feature is built around, covered below. This is also the CLI's own consumer of the same registry-advertised catalog that feeds darkmux acp's editor integration for Zed: radio is the terminal-native way to use that same catalog without an editor in the loop.

Two seats, one exchange

radio is built on two distinct dispatches, each staffed by its own role, because the two jobs have different shapes:

  • The routing seat (radio-router, role_family: utility) does bounded classification. It's handed your text plus the full list of advertised commands (id + description + optional hint) and returns exactly one JSON object: a chosen command and its trailing args, or a refusal with a reason. No agent loop, no tools, no free-form output. It can only choose among the closed set it was given.
  • The answering seat (radio-host, role_family: specialist) is dispatched only when the routing seat refuses. It reads a compiled bundle of local facts: the command catalog, live config, a mission-board summary, and so on (see the grounding boundary below), and replies in prose, in persona. It has no tools either: every fact it can cite was already gathered deterministically and handed to it before it ever runs.

Splitting the two matters because they're asymmetric jobs: routing is small, bounded I/O well suited to a fast utility-class model; answering needs enough headroom to reply with some personality, which is why it defaults to your normal specialist tier rather than the compact utility binding. One exchange, one routing call, at most one more dispatch for the answer. Never a loop, never a retry-on-refusal.

Inspect either role like any other: darkmux role show radio-router or darkmux role show radio-host.

Using it

The built-in registry ships with exactly one command advertised today: review. Anything else you want radio to route to is a mission config in ~/.darkmux/mission-configs/ carrying its own panel block (see the catalog below). A live example against the built-in:

darkmux radio "please review my changes"
# radio: routing to /review — from your text
# radio: launching `review` …
# (mission launch's own interactive sign-off gate applies from here)

A routed command that spawns a mission (the review pipeline, or any model-seated command you've added) runs as a real darkmux mission launch <id> child process inheriting your terminal. The same interactive sign-off gate you'd see running that command directly applies unchanged. A routed command whose graph is entirely procedural (no model dispatch at all) runs in-process instead, with no mission instance minted.

Spoken "review this" reviews your uncommitted working-tree diff (git diff HEAD), not the branch-vs-base diff darkmux mission launch review uses when run directly. If there's nothing uncommitted, radio says so and stops:

radio: no uncommitted changes to review in this working tree.

See the plan before it runs with --dry-run, which prints the resolved route and exits without executing anything. The routing line prints the same way as the live example above; only the added dry-run line is new:

darkmux radio "please review my changes" --dry-run
# radio: --dry-run — would invoke `review` with no arguments

If your text carries trailing args past the matched command's intent, the dry-run line names them too (would invoke `<id>` with args: "<text>"). If nothing is currently advertised at all (no mission config anywhere declares a panel block), radio says so up front and does nothing:

radio: no commands are currently advertised.
No mission config in the merged registry (built-ins + ~/.darkmux/mission-configs/) declares a `panel` block.

The command catalog: what's advertised

radio only ever routes to what's already advertised. It never composes a new action out of your words. A mission config becomes routable by adding a top-level panel block:

{
  "id": "my-command",
  "name": "My Command",
  "panel": {
    "description": "One-line label for the command palette.",
    "hint": "optional input hint shown before you type anything"
  }
}

panel.description is what the routing seat actually reads to decide whether your text matches. It's deliberately the short palette label, never a mission config's own top-level description field (which tends to be long-form engineering provenance, unsuitable for a model deciding "does this text mean run this command").

How a routed command actually executes depends on what its graph declares, structurally, not on its id or name:

  • A graph using review-pipeline step kinds routes to the dedicated review launcher (the same path mission launch review itself uses).
  • A graph whose every step is procedural (no model dispatch anywhere in it) runs ephemeral, in-process, with no mission instance minted.
  • Anything else (at least one model-seated step) launches as a normal darkmux mission launch <id> subprocess.

See Task/Step graphs: authoring an automated phase for the full mission-config shape and step-kind reference.

Worked example: gated forge verbs

The catalog above is generic on purpose. darkmux doesn't ship pull-request verbs itself: GitHub, GitLab, and Perforce shops each want a different vocabulary, so an ecosystem tool never graduates into a built-in. Forge-specific commands are configs you write and keep in ~/.darkmux/mission-configs/, following the pattern in this section (#1685). gh never appears inside darkmux; it appears in the shell command your own config runs.

The pattern combines three pieces: a panel block for the catalog, a procedural.shell step for the actual work, and a gate: "operator" step property for anything that changes state. Here's pr-merge:

{
  "id": "pr-merge",
  "name": "PR Merge",
  "panel": {
    "description": "Merge a pull request once every check is green.",
    "hint": "[PR number]"
  },
  "phases": [
    {
      "id": "run",
      "tasks": [
        {
          "id": "merge-task",
          "description": "merge the named PR",
          "reads": ["__panel_args__"],
          "steps": [
            {
              "id": "merge-step",
              "kind": "procedural.shell",
              "gate": "operator",
              "config": {
                "command": "gh pr merge $DARKMUX_STEP_INPUT___PANEL_ARGS__ --squash --delete-branch"
              }
            }
          ]
        }
      ]
    }
  ]
}

reads: ["__panel_args__"] is the reserved id that hands a task the raw text you typed after the command name, an empty string when you typed none. darkmux exposes it to the shell step as the environment variable named in the command above. The gate: "operator" property means the step doesn't run until you confirm it: the editor's native permission dialog in the panel, a y/N prompt at an interactive terminal, or a blocked pending sign-off from a non-interactive launch. radio "merge 422" routes here, the routing seat carries the PR number as the trailing arg, and the merge itself waits on your confirm either way.

pr-list (read-only, no gate key at all) and pr-approve (gated, posts your review text as the rest-of-line) follow the identical shape: a panel block for the catalog entry, one procedural.shell step running your own gh invocation, and gate: "operator" on anything past a plain read. Write the config once and radio routes free text onto it exactly like any built-in.

Fail closed: refuse, don't guess

Every failure mode the routing seat can hit (empty output, malformed JSON, a command name outside the catalog, more than one fenced block in the response) becomes a refusal, never a guess and never a crash. The routing seat's own instructions put it plainly: when in doubt, refuse; a wrong refusal costs you one extra step, a wrong route runs the wrong command.

A refusal at the CLI doesn't just print the reason and stop. The same text is handed to the answering seat for a grounded, in-persona reply first:

darkmux radio "what's slow about my last review"
# radio: <the answering seat's prose reply, possibly naming a /command to run>

Only if that dispatch itself fails (no model loaded, a timeout) does radio fall back to the bare refusal plus a plain command listing, never silently swallowed:

radio: the answering seat failed (...); falling back to the plain refusal
radio: <reason>
Available commands: `/review`.

One CLI-specific limitation worth knowing: the CLI has no persistent session, so every invocation answers against a fresh, empty recent-output shelf (the last few rendered command outputs a longer-lived session, like the editor integration, would carry forward). That's a documented limitation of one-shot terminal use, not a bug.

Configuration

Three knobs, all under the radio config block. darkmux init writes them visible with their defaults, same as every other config surface:

"radio": { "router_profile": "", "answerer_profile": "", "humor": 65 }
Config keyEnv overrideDefaultEffect
radio.router_profile DARKMUX_RADIO_ROUTER_PROFILE unset Explicit profile for the routing seat. Empty/unset falls through to role_profiles.radio-router if you've bound one, then default_profile.
radio.answerer_profile DARKMUX_RADIO_ANSWERER_PROFILE unset Explicit profile for the answering seat. Same fall-through: role_profiles.radio-host, then default_profile.
radio.humor DARKMUX_RADIO_HUMOR 65 0-100 dial substituted into the answering persona's prompt. Values outside that range are accepted by config set but clamped to 0..=100 when actually read.

Set them the same way as any other config field:

darkmux config set radio.router_profile <profile-name>
darkmux config set radio.answerer_profile <profile-name>
darkmux config set radio.humor 80
darkmux config get radio.humor

An explicit radio.*_profile setting always wins over an existing role_profiles.radio-router / role_profiles.radio-host pin, the same precedence every other profile override in darkmux uses. Leaving both set is harmless; the more specific one wins.

Tuning live from the editor

If you're driving darkmux through the editor integration (darkmux acp), the answering seat's staffing is also available as two live session config options: a "Radio host" picker listing every profile in your registry plus "Use configured default," and a "Radio humor" picker offering four presets (10, 35, 65, 90). Both are session-scoped: changing one re-staffs the answering seat for the rest of that session without touching config.json, and the routing seat's own staffing is unaffected either way. Reach for radio.answerer_profile/radio.humor for a durable default; reach for the pickers when you want to try a different host mid-session without leaving the thread.

The grounding boundary

The answering seat's replies are grounded in real local facts, assembled deterministically before the one model call it makes: the command catalog, the current darkmux config list output, a compact mission-board summary, your session's recent command outputs, and (when your message names one) one mission's full detail. The seat itself has no tools and can't fetch any of this on its own; it only ever sees what was already gathered and handed to it in the message.

What actually gets assembled depends on where that grounding is headed. If the resolved radio-host profile is served locally, everything above is in scope. If it resolves to a remote, hosted endpoint instead, the grounding narrows automatically to what's already public: the command catalog and the CLI's own --help text. The config surface, the mission-board summary, your session's recent outputs, and any named mission detail are withheld. They never leave the machine.

Why this boundary exists.

After a review, the recent-outputs shelf holds rendered output over your own private diff. The config block carries machine ids, URLs, and directory layout. Mission ids can encode repository names and commit SHAs. None of that is safe to hand to a model you don't control the serving of, so the gate checks where the answering seat resolves before assembling anything, not after. This mirrors darkmux's existing rule that a machine's identity context is withheld from every remote endpoint, approved ones included. A grounding bundle is strictly more sensitive.

Practically: if you want radio's answers to be specific about this machine's state (what's running, what config you've set, what a named mission looks like), keep radio.answerer_profile pointed at a local profile. Pointing it at a remote/hosted profile is safe (nothing private leaves), but answers about your own local state will be honestly limited to "that's outside what I can ground an answer in from here," since the seat's persona refuses to invent facts it wasn't handed.

Where this fits

radio sits on top of the same registry and dispatch machinery the rest of the advanced surface uses. If you haven't read it yet, Missions, phases, and dispatch covers roles, mission configs, and the review funnel radio routes into by default. Everything radio does (dispatching a role, launching a mission, running the review funnel) you can also do directly with the commands named throughout that page. radio is a shortcut over the same primitives, not a separate system.
