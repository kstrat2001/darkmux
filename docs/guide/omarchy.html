Omarchy: darkmux on Linux

darkmux was built on macOS. This page is the path on Omarchy, an Arch Linux setup, on an Apple Silicon Mac running the Asahi kernel: build from source, serve a model on the Apple GPU without LM Studio, and set up what Linux does not give you for free. Linux support lives on the omarchy support branch until it reaches a release, and this page follows that branch; the last section says what does not work yet.

Build and install

There is no Homebrew here, so darkmux builds from source, from the omarchy branch: it carries the Linux platform fixes (a container that can reach the host and its own files, a machine identity, the hardware line on the fleet card) that are not in a release yet. Omarchy ships mise; it installs the Rust toolchain the repo pins without touching the system.

mise use -g rust@1.97.1
cargo install --git https://github.com/kstrat2001/darkmux --branch omarchy --locked darkmux
ln -sf ~/.cargo/bin/darkmux ~/.local/bin/darkmux   # ~/.cargo/bin is not on Omarchy's PATH
darkmux --version
darkmux init

Re-run the cargo install line to update. init writes ~/.darkmux/config.json and profiles.json and installs the agent skills. With no LM Studio it cannot fill in a worker model; the model section below adds one.

A local model without LM Studio

omarchy-mlx runs Apple's MLX on the Mac's GPU through Mesa's Honeykrisp Vulkan driver, and installs mlx_lm.server, which serves the OpenAI chat API. darkmux reaches it as an unmanaged endpoint: darkmux only sends requests, and the server owns what is loaded. Install it from the Omarchy menu (Install > AI) or with the project's script, then serve a model sized for your memory:

~/.local/share/mlx-omarchy/venv/bin/mlx_lm.server \
  --model mlx-community/Qwen3-1.7B-4bit --host 127.0.0.1 --port 8080 \
  --prefill-step-size 512 --prompt-cache-size 1 --decode-concurrency 1 \
  --chat-template-args '{"enable_thinking":false}'

Then add an endpoint and a profile to ~/.darkmux/profiles.json:

"profiles": {
  "mlx-small": {
    "description": "Qwen3-1.7B on the local mlx_lm.server.",
    "models": [{ "id": "mlx-community/Qwen3-1.7B-4bit", "endpoint": "mlx-local" }]
  }
},
"endpoints": {
  "mlx-local": { "url": "http://127.0.0.1:8080/v1", "dialect": "chat-completions-max-tokens" }
}

A role with no tools runs on the host against that endpoint, with no Docker and no LM Studio:

darkmux dispatch pr-reviewer --profile mlx-small "In two sentences: what is one risk of merging a change that adds a new required config field?"

Verified 2026-10-11 on a 13" M2 MacBook Pro (8 GB), omarchy-mlx v0.7.32, system Mesa 26.2.4: the dispatch returned a verdict in about a minute, the model's first load included. On 8 GB, Qwen3-4B-Instruct-2507-4bit ran the GPU out of memory on a ~3.5k-token prompt; stay at 1.7B there, or close other GPU users.

Docker, for roles with tools

Every role with tools (coder, reviewer, lab workloads) runs in the darkmux-runtime container. On macOS, Docker Desktop hides two differences that Docker Engine on Linux does not, and darkmux's Linux platform strategy (darkmux-platform) handles both:

  • Reaching the host. Docker Desktop defines host.docker.internal and forwards it to the Mac's own 127.0.0.1. Docker Engine defines neither, so darkmux maps the name to the bridge gateway (--add-host=host.docker.internal:host-gateway). The model server then has to listen on the bridge, and the firewall has to let that one port in.
  • Who owns the files. darkmux creates each dispatch's workspace and output directories private to you. Docker Desktop maps ownership across those mounts; Docker Engine keeps it, so the container runs as you (--user=<your uid>:<your gid>). Override it with darkmux config set runtime.container_user <uid>:<gid>, or image for the image's own user.

The rest is yours to run, because darkmux never runs sudo:

sudo usermod -aG docker "$USER"
sudo systemctl enable --now docker.service
sudo ufw allow in on docker0 to any port 8080 proto tcp
sudo ufw status verbose

Log out and back in for the group to apply. Then serve the model on the bridge address (--host 172.17.0.1, Omarchy's Docker bridge) instead of 127.0.0.1, so only containers reach it, and point the endpoint at http://host.docker.internal:8080/v1. A model on an endpoint darkmux does not manage needs its context window declared for a role with tools, which compacts against it: add "n_ctx": 32768 (or the model's real window) to the profile's model.

darkmux dispatch code-reviewer --profile mlx-small "Use the exec tool to run: echo hello-from-container. Then reply with the output in one sentence."

Verified 2026-10-11 on the same M2 with a build of the omarchy branch: two turns, one real exec tool call in the container, exit 0, 79 s.

darkmux keeps the container on its own network rather than the host's. Host networking would make a 127.0.0.1 server reachable with no setup at all, and it would also give every tool call the run of every port on the machine.

Keep the daemon running

darkmux serve runs the viewer (http://127.0.0.1:8765/), presence, and the flow sinks a fleet reads. On macOS Homebrew's brew services keeps it up; on Omarchy it is a systemd user service:

mkdir -p ~/.config/systemd/user
cat > ~/.config/systemd/user/darkmux-serve.service <<'UNIT'
[Unit]
Description=darkmux serve daemon (viewer, fleet presence, flow sinks)
After=network-online.target

[Service]
ExecStart=%h/.cargo/bin/darkmux serve
Restart=on-failure

[Install]
WantedBy=default.target
UNIT
systemctl --user daemon-reload
systemctl --user enable --now darkmux-serve
journalctl --user -u darkmux-serve -n 20

The daemon reads config.json once at start: after a darkmux config set, run systemctl --user restart darkmux-serve.

Join a fleet

A fleet is a few of your machines on a Tailscale tailnet, streaming flow records to one hub's Redis, so every machine's viewer shows every machine. The full model is in the fleet guide; this is the Omarchy part.

Tailscale

Tailscale is in Arch's repositories. Update the system first: a stale package database asks the mirror for a file it no longer has (404), and refreshing the database without upgrading (pacman -Sy alone) leaves a partial upgrade, which Arch does not support.

omarchy-update                          # or: sudo pacman -Syu
sudo pacman -S tailscale
sudo systemctl enable --now tailscaled
sudo tailscale set --operator=$USER     # tailscale status / ping without sudo
sudo tailscale up                       # prints a login URL
tailscale ping <hub's tailnet address>

Name it for the OS, especially on a dual-boot Mac

Asahi installs alongside macOS, so one Mac can boot either. darkmux treats each install as its own machine: macOS identifies itself by its IOPlatformUUID, which Linux cannot read, and Linux by its /etc/machine-id. So the same laptop is two machines in the fleet, one per OS, never online together. Give the Linux side its own name with omarchy in it, on the tailnet and in darkmux, so each card says which OS it is; otherwise Tailscale names the second install <name>-1.

sudo tailscale set --hostname omarchy-book
darkmux config set machine_id omarchy-book

Showing one dual-boot laptop as one card, labeled with whichever OS is running, is planned (#3212).

Point it at the hub

darkmux config set fleet.mode peer
darkmux config set redis.enabled true
darkmux config set redis.host <hub's tailnet address>
systemctl --user restart darkmux-serve
darkmux doctor
darkmux flow note --text "hello from omarchy"

The note appears in every fleet viewer, and the machine shows as a card with its name and hardware (Apple M2 · 8 GB). The daemon's log says presence: heartbeat emitter started — uid=… display=…. In doctor, expect the rows whose probes are macOS-only to warn rather than pass (RAM headroom, the host probe, the heuristics provider), and lms binary to fail with no LM Studio. A Redis with no password warns on redis config; on a password-less, tailnet-only hub that is expected. Linux has no Keychain, so a password or a fleet token comes from DARKMUX_REDIS_URL or DARKMUX_SERVE_TOKEN in the daemon's environment.

Verified 2026-10-12: a 13" M2 on Omarchy joined a fleet hubbed on a Mac Studio over Tailscale; its note and presence reached the hub, and its card read omarchy-book. Taking work from other machines (fleet trust, the serve token) is not covered yet.

What does not work yet

  • radio and compaction run on the utility model, which only LM Studio can serve today (#3207).
  • Machine telemetry (CPU, memory, GPU, power) reads empty, and the residency planner sees no memory pools, until the host probe and the memory snapshot have Linux strategies.
  • A role with no tools on an unmanaged endpoint runs host-side and writes no live state, so the fleet card reads PROMPT for the whole call (#3211). Prompt-processing progress isn't shown yet either (#3210).
  • A 127.0.0.1 endpoint from inside the container. darkmux rewrites a loopback LM Studio address for the container, but not an unmanaged endpoint's URL, so a role with tools on a 127.0.0.1 endpoint dials the container itself. Use host.docker.internal in the endpoint URL (#3209).
  • darkmux doctor fails the lms binary row with no LM Studio installed, and warns on rows whose probes are macOS-only.
  • A model server that runs out of GPU memory mid-request can stop answering without closing the connection; darkmux then waits out its full timeout.
