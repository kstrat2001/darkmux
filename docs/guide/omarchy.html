Omarchy: darkmux on Linux

darkmux was built on macOS. This page is the path on Omarchy, an Arch Linux setup, on an Apple Silicon Mac running the Asahi kernel: build from source, serve a model on the Apple GPU without LM Studio, and set up what Linux does not give you for free. Linux support is in progress; the last section says what does not work yet.

Build and install

There is no Homebrew here, so darkmux builds from source. Omarchy ships mise; it installs the Rust toolchain the repo pins without touching the system.

mise use -g rust@1.97.1
git clone https://github.com/kstrat2001/darkmux ~/Work/darkmux
cd ~/Work/darkmux
cargo install --path . --locked
ln -sf ~/.cargo/bin/darkmux ~/.local/bin/darkmux   # ~/.cargo/bin is not on Omarchy's PATH
darkmux init

init writes ~/.darkmux/config.json and profiles.json and installs the agent skills. With no LM Studio it cannot fill in a worker model; the next section adds one.

A local model without LM Studio

omarchy-mlx runs Apple's MLX on the Mac's GPU through Mesa's Honeykrisp Vulkan driver, and installs mlx_lm.server, which serves the OpenAI chat API. darkmux reaches it as an unmanaged endpoint: darkmux only sends requests, and the server owns what is loaded. Install it from the Omarchy menu (Install > AI) or with the project's script, then serve a model sized for your memory:

~/.local/share/mlx-omarchy/venv/bin/mlx_lm.server \
  --model mlx-community/Qwen3-1.7B-4bit --host 127.0.0.1 --port 8080 \
  --prefill-step-size 512 --prompt-cache-size 1 --decode-concurrency 1 \
  --chat-template-args '{"enable_thinking":false}'

Then add an endpoint and a profile to ~/.darkmux/profiles.json:

"profiles": {
  "mlx-small": {
    "description": "Qwen3-1.7B on the local mlx_lm.server.",
    "models": [{ "id": "mlx-community/Qwen3-1.7B-4bit", "endpoint": "mlx-local" }]
  }
},
"endpoints": {
  "mlx-local": { "url": "http://127.0.0.1:8080/v1", "dialect": "chat-completions-max-tokens" }
}

A role with no tools runs on the host against that endpoint, with no Docker and no LM Studio:

darkmux dispatch pr-reviewer --profile mlx-small "In two sentences: what is one risk of merging a change that adds a new required config field?"

Verified 2026-10-11 on a 13" M2 MacBook Pro (8 GB), omarchy-mlx v0.7.32, system Mesa 26.2.4: the dispatch returned a verdict in about a minute, the model's first load included. On 8 GB, Qwen3-4B-Instruct-2507-4bit ran the GPU out of memory on a ~3.5k-token prompt; stay at 1.7B there, or close other GPU users.

Docker, for roles with tools

Not yet verified end to end on Omarchy. Every role with tools (coder, reviewer, lab workloads) runs in the darkmux-runtime container. On macOS, Docker Desktop lets a container reach a server on the Mac's 127.0.0.1 as host.docker.internal. Docker Engine on Linux does neither: the name is not defined, and a container reaches the host over the docker0 bridge, so the server has to listen there and the firewall has to let that one port in. darkmux maps the name for you on Linux (darkmux-platform); the rest is yours to run, because darkmux never runs sudo:

sudo usermod -aG docker "$USER"
sudo systemctl enable --now docker.service
sudo ufw allow in on docker0 to any port 8080 proto tcp
sudo ufw status verbose

Log out and back in for the group to apply. Then serve the model on the bridge address instead of 127.0.0.1 (--host 172.17.0.1, Omarchy's Docker bridge), so only containers reach it.

darkmux keeps the container on its own network rather than the host's. Host networking would make a 127.0.0.1 server reachable with no setup at all, and it would also give every tool call the run of every port on the machine.

What does not work yet

  • radio and compaction run on the utility model, which only LM Studio can serve today (#3207).
  • darkmux doctor fails the lms binary row with no LM Studio installed, and warns on rows whose probes are macOS-only: RAM headroom, the host probe, machine uid.
  • The viewer's machine facts (memory, CPU, power) are empty, and the residency planner sees no memory pools, until each probe has a Linux strategy.
  • A model server that runs out of GPU memory mid-request can stop answering without closing the connection; darkmux then waits out its full timeout.
