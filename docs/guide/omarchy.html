Omarchy: darkmux on Linux

darkmux was built on macOS. This page is the path on Omarchy, an Arch Linux setup, on an Apple Silicon Mac running the Asahi kernel: build from source, serve a model on the Apple GPU without LM Studio, and set up what Linux does not give you for free. Linux support lives on the omarchy support branch until it reaches a release, and this page follows that branch; the last section says what does not work yet.

Build and install

There is no Homebrew here, so darkmux builds from source, from the omarchy branch: it carries the Linux platform fixes (a container that can reach the host and its own files, a machine identity, the hardware line on the fleet card) that are not in a release yet. Omarchy ships mise; it installs the Rust toolchain the repo pins without touching the system.

mise use -g rust@1.97.1
cargo install --git https://github.com/kstrat2001/darkmux --branch omarchy --locked darkmux
ln -sf ~/.cargo/bin/darkmux ~/.local/bin/darkmux   # ~/.cargo/bin is not on Omarchy's PATH
darkmux --version
darkmux init

Verified 2026-10-12 on a 13" M2 (8 GB): the cargo install --git line built the branch in under four minutes with other memory users closed. --version may show a ✱ after the commit: cargo's checkout looks modified to the build's git probe; the build is the commit named.

Re-run the cargo install line to update. init writes ~/.darkmux/config.json and profiles.json and installs the agent skills. With no LM Studio it cannot fill in a worker model; the model section below adds one.

A local model without LM Studio

omarchy-mlx runs Apple's MLX on the Mac's GPU through Mesa's Honeykrisp Vulkan driver, and installs mlx_lm.server, which serves the OpenAI chat API. darkmux reaches it as an unmanaged endpoint: darkmux only sends requests, and the server owns what is loaded.

Install omarchy-mlx

The Omarchy menu's entry (Install > AI) checks the chip and refuses any it hasn't been tested on, a base M2 included. The project's own installer warns instead and carries on. It needs openblas, and installs the rest under ~/.local/share/mlx-omarchy. Read the script before running it:

sudo pacman -S --needed lapack blas openblas
curl -fsSL https://raw.githubusercontent.com/joshuaswarren/omarchy-mlx/main/install.sh -o mlx-install.sh
less mlx-install.sh
bash mlx-install.sh

It ends with a smoke test that names your GPU and runs a matrix multiply on it. If a download fails partway (it fetches its patches one by one from GitHub), run it again.

Pick a model that fits

The model shares memory with everything else on the machine, and its working memory (the KV cache) grows with the prompt. darkmux's role prompts alone are about 3,500 tokens. On an 8 GB M2, mlx-community/Qwen3-1.7B-4bit runs them; Qwen3-4B-Instruct-2507-4bit ran the GPU out of memory on the same prompt. With more memory, go bigger.

Serve it as a user service

A systemd user unit keeps the server up across logouts and reboots (with linger, under "Run it headless" below):

cat > ~/.config/systemd/user/mlx-local.service <<'UNIT'
[Unit]
Description=mlx_lm.server on 127.0.0.1:8080
After=network-online.target

[Service]
ExecStart=%h/.local/share/mlx-omarchy/venv/bin/mlx_lm.server --model mlx-community/Qwen3-1.7B-4bit --host 127.0.0.1 --port 8080 --prefill-step-size 512 --prompt-cache-size 1 --decode-concurrency 1 --chat-template-args '{"enable_thinking":false}'
Restart=on-failure

[Install]
WantedBy=default.target
UNIT
systemctl --user daemon-reload
systemctl --user enable --now mlx-local
curl -s http://127.0.0.1:8080/v1/models

Keep the single quotes around the JSON: systemd strips double quotes from ExecStart, and without the single quotes the server receives {enable_thinking:false} and exits. The flags keep memory down on a small machine: smaller prefill steps (512), one cached prompt, one request at a time. enable_thinking: false turns off Qwen3's reasoning preamble, so a short answer stays short.

Then add an endpoint and a profile to ~/.darkmux/profiles.json:

"profiles": {
  "mlx-small": {
    "description": "Qwen3-1.7B on the local mlx_lm.server.",
    "models": [{ "id": "mlx-community/Qwen3-1.7B-4bit", "endpoint": "mlx-local" }]
  }
},
"endpoints": {
  "mlx-local": { "url": "http://127.0.0.1:8080/v1", "dialect": "chat-completions-max-tokens" }
}

A role with no tools runs on the host against that endpoint, with no Docker and no LM Studio:

darkmux dispatch pr-reviewer --profile mlx-small "In two sentences: what is one risk of merging a change that adds a new required config field?"

Verified 2026-10-11 on a 13" M2 MacBook Pro (8 GB), omarchy-mlx v0.7.32, system Mesa 26.2.4: the dispatch returned a verdict in about a minute, the model's first load included. On 8 GB, Qwen3-4B-Instruct-2507-4bit ran the GPU out of memory on a ~3.5k-token prompt; stay at 1.7B there, or close other GPU users.

Docker, for roles with tools

Every role with tools (coder, reviewer, lab workloads) runs in the darkmux-runtime container. On macOS, Docker Desktop hides two differences that Docker Engine on Linux does not, and darkmux's Linux platform strategy (darkmux-platform) handles both:

  • Reaching the host. Docker Desktop defines host.docker.internal and forwards it to the Mac's own 127.0.0.1. Docker Engine defines neither, so darkmux maps the name to the bridge gateway (--add-host=host.docker.internal:host-gateway). The model server then has to listen on the bridge, and the firewall has to let that one port in.
  • Who owns the files. darkmux creates each dispatch's workspace and output directories private to you. Docker Desktop maps ownership across those mounts; Docker Engine keeps it, so the container runs as you (--user=<your uid>:<your gid>). Override it with darkmux config set runtime.container_user <uid>:<gid>, or image for the image's own user.

The rest is yours to run, because darkmux never runs sudo:

sudo usermod -aG docker "$USER"
sudo systemctl enable --now docker.service
sudo ufw allow in on docker0 to any port 8080 proto tcp
sudo ufw status verbose

Log out and back in for the group to apply. Then serve the model on the bridge address (--host 172.17.0.1, Omarchy's Docker bridge) instead of 127.0.0.1, so only containers reach it, and point the endpoint at http://host.docker.internal:8080/v1. A model on an endpoint darkmux does not manage needs its context window declared for a role with tools, which compacts against it: add "n_ctx": 32768 (or the model's real window) to the profile's model.

darkmux dispatch code-reviewer --profile mlx-small "Use the exec tool to run: echo hello-from-container. Then reply with the output in one sentence."

Verified 2026-10-11 on the same M2 with a build of the omarchy branch: two turns, one real exec tool call in the container, exit 0, 79 s.

darkmux keeps the container on its own network rather than the host's. Host networking would make a 127.0.0.1 server reachable with no setup at all, and it would also give every tool call the run of every port on the machine.

Keep the daemon running

darkmux serve runs the viewer (http://127.0.0.1:8765/), presence, and the flow sinks a fleet reads. On macOS Homebrew's brew services keeps it up; on Omarchy it is a systemd user service:

mkdir -p ~/.config/systemd/user
cat > ~/.config/systemd/user/darkmux-serve.service <<'UNIT'
[Unit]
Description=darkmux serve daemon (viewer, fleet presence, flow sinks)
After=network-online.target

[Service]
ExecStart=%h/.cargo/bin/darkmux serve
Restart=on-failure

[Install]
WantedBy=default.target
UNIT
systemctl --user daemon-reload
systemctl --user enable --now darkmux-serve
journalctl --user -u darkmux-serve -n 20

The daemon reads config.json once at start: after a darkmux config set, run systemctl --user restart darkmux-serve.

Join a fleet

A fleet is a few of your machines on a Tailscale tailnet, streaming flow records to one hub's Redis, so every machine's viewer shows every machine. The full model is in the fleet guide; this is the Omarchy part.

Tailscale

Tailscale is in Arch's repositories. Update the system first: a stale package database asks the mirror for a file it no longer has (404), and refreshing the database without upgrading (pacman -Sy alone) leaves a partial upgrade, which Arch does not support.

omarchy-update                          # or: sudo pacman -Syu
sudo pacman -S tailscale
sudo systemctl enable --now tailscaled
sudo tailscale set --operator=$USER     # tailscale status / ping without sudo
sudo tailscale up                       # prints a login URL
tailscale ping <hub's tailnet address>

Name it for the OS, especially on a dual-boot Mac

Asahi installs alongside macOS, so one Mac can boot either. darkmux treats each install as its own machine: macOS identifies itself by its IOPlatformUUID, which Linux cannot read, and Linux by its /etc/machine-id. So the same laptop is two machines in the fleet, one per OS, never online together. Give the Linux side its own name with omarchy in it, on the tailnet and in darkmux, so each card says which OS it is; otherwise Tailscale names the second install <name>-1.

sudo tailscale set --hostname omarchy-book
darkmux config set machine_id omarchy-book

Showing one dual-boot laptop as one card, labeled with whichever OS is running, is planned (#3212).

Point it at the hub

darkmux config set fleet.mode peer
darkmux config set redis.enabled true
darkmux config set redis.host <hub's tailnet address>
systemctl --user restart darkmux-serve
darkmux doctor
darkmux flow note --text "hello from omarchy"

The note appears in every fleet viewer, and the machine shows as a card with its name and hardware (Apple M2 · 8 GB). The daemon's log says presence: heartbeat emitter started — uid=… display=…. In doctor, expect the rows whose probes are macOS-only to warn rather than pass (RAM headroom, the host probe, the heuristics provider), and lms binary to fail with no LM Studio. A Redis with no password warns on redis config; on a password-less, tailnet-only hub that is expected. Linux has no Keychain, so a password or a fleet token comes from DARKMUX_REDIS_URL or DARKMUX_SERVE_TOKEN in the daemon's environment.

Open a runner's viewer from any tailnet device

The daemon listens on 127.0.0.1:8765 only, and darkmux won't bind it elsewhere without read auth. To open this machine's viewer from your phone or another machine, forward a tailnet-only port to it with systemd: nothing listens on Wi-Fi, and the daemon stays on loopback. Put your machine's tailnet address (tailscale ip -4) in ListenStream:

cat > ~/.config/systemd/user/darkmux-viewer-tailnet.socket <<'UNIT'
[Unit]
Description=darkmux viewer on the tailnet (:8090 -> 127.0.0.1:8765)

[Socket]
ListenStream=<tailnet address>:8090
FreeBind=true

[Install]
WantedBy=sockets.target
UNIT
cat > ~/.config/systemd/user/darkmux-viewer-tailnet.service <<'UNIT'
[Unit]
Description=Forward the tailnet viewer port to the darkmux daemon
Requires=darkmux-viewer-tailnet.socket
After=darkmux-viewer-tailnet.socket

[Service]
ExecStart=/usr/lib/systemd/systemd-socket-proxyd 127.0.0.1:8765
UNIT
systemctl --user daemon-reload
systemctl --user enable --now darkmux-viewer-tailnet.socket
sudo ufw allow in on tailscale0 to any port 8090 proto tcp

Then open http://omarchy-book:8090/ on any device with Tailscale connected (MagicDNS resolves the short name). FreeBind lets the socket start before Tailscale has brought the address up. darkmux treats a request through a plain forward like this as remote, so its panels withhold this machine's addresses and paths, as for any remote viewer; fleet cards and runs show in full. To watch the whole fleet, a hub's viewer that's already on the tailnet works the same way.

Verified 2026-10-12: http://omarchy-book:8090/ opened from an iPhone on the tailnet.

Verified 2026-10-12: a 13" M2 on Omarchy joined a fleet hubbed on a Mac Studio over Tailscale; its note and presence reached the hub, and its card read omarchy-book. Taking work from other machines (fleet trust, the serve token) is not covered yet.

Optional: run it headless

Everything above works with the desktop up. This section is optional: once the machine is on the fleet, its card and runs show in the viewer on every other machine, so it doesn't need its own screen, and it can run as a headless AI runner on your tailnet: models, Docker and darkmux running, reachable over SSH, watched from the fleet viewer.

The bonus is memory. On Apple Silicon the GPU shares system memory, so the desktop (the compositor, the bar, every rendered window) comes out of the same pool as the model. Lowering the resolution saves little (a 2560×1600 frame is about 16 MB); not running the desktop is what counts. An example, on the 13" M2 (8 GB) this page was written on, with the Qwen3-1.7B server running:

Available memoryUsed
Desktop up (Hyprland, the bar, a terminal)3,628 MB3,906 MB
Headless (SDDM stopped, from a text console)4,953 MB2,581 MB
Freed+1,325 MB−1,325 MB

From free -m on 2026-10-12, both with the model server running: the desktop row at 01:49, the headless row after step 5. About 1.3 GB, nearly a fifth of the machine's usable memory, back for models and builds.

Run each step in order. The first two are what keep it running; skipping them is how a headless node silently drops off the fleet.

1. Stay awake with the lid closed (on power)

By default closing a laptop's lid suspends it. Ignore the lid while it's on external power, and keep suspending on battery, which protects the battery:

sudo mkdir -p /etc/systemd/logind.conf.d
printf '[Login]\nHandleLidSwitchExternalPower=ignore\n' | sudo tee /etc/systemd/logind.conf.d/30-headless-lid.conf
sudo systemctl restart systemd-logind   # may end the current desktop session

2. Keep your user services running without a login

darkmux-serve and mlx-local are user services: by default they stop when your last session ends. Linger keeps them running from boot, logged in or not:

sudo loginctl enable-linger "$USER"
loginctl show-user "$USER" -p Linger      # Linger=yes

3. Check every piece starts at boot

for u in tailscaled docker sshd; do echo "$u $(systemctl is-enabled $u) $(systemctl is-active $u)"; done
for u in darkmux-serve mlx-local; do echo "$u $(systemctl --user is-enabled $u) $(systemctl --user is-active $u)"; done

Tailscale, Docker and SSH are system services: they start at boot whether anyone is logged in. Each line should say enabled active. (containerd shows as not enabled; Docker starts it.) A user unit made with systemd-run says transient: it doesn't survive a reboot, so write it as a unit file as above.

4. Reach it over the tailnet

The simplest way in is Tailscale SSH: Tailscale authenticates you by your tailnet login, so there are no keys to copy to each device, and it works from a phone. On the runner:

sudo tailscale set --ssh

Then, from any device on the tailnet, including a phone with an SSH app (Blink Shell, Termius) and Tailscale connected, connect by the name you gave the runner, with no password or key:

ssh <you>@omarchy-book
darkmux doctor
systemctl --user status darkmux-serve mlx-local

Depending on your tailnet's access policy, the first connection (and one every so often after) prints a login.tailscale.com link to approve in a browser. Plain OpenSSH works too (the runner's sshd already listens): add each device's public key to ~/.ssh/authorized_keys, allow it through the firewall only on the tailnet (sudo ufw allow in on tailscale0 to any port 22 proto tcp), and once a key works, turn passwords off (PasswordAuthentication no in a file under /etc/ssh/sshd_config.d/).

Tailscale SSH verified 2026-10-12 from an iPhone on the tailnet to the M2.

Its viewer is on the machine itself (http://127.0.0.1:8765/); from elsewhere, the fleet viewer on any other machine shows its card and runs.

5. Turn the desktop off

Omarchy logs you straight into Hyprland at boot (SDDM autologin), and logging out doesn't help: SDDM logs you straight back in. Stop the display manager instead, from a text console so nothing you need is inside the desktop when it goes: press Ctrl+Alt+F3, log in, and run:

sudo systemctl stop sddm       # ends Hyprland and everything in it; user services keep running (linger)
free -m                        # the memory the desktop was holding is back
sudo systemctl start sddm      # the desktop again, for this boot

A terminal and an agent can run right there in the text console, on the machine, with no desktop. Stopping SDDM lasts until the next boot, which brings the desktop back.

Optional: to boot without the desktop every time, for a machine that only serves the fleet:

sudo systemctl set-default multi-user.target    # boot to a text console; no desktop
sudo systemctl set-default graphical.target     # undo: the desktop at boot again
sudo systemctl start sddm                       # the desktop now, for one session

Anything running inside the desktop session ends with it, a terminal and an agent in it included; run those in the text console or over SSH instead.

Dim the screen with the lid open

The text console never blanks by default (consoleblank=0), so a runner left with its lid open keeps its backlight on. Turn it off; logind lets the user at the machine set it, so no sudo:

brightnessctl -d apple-panel-bl set 0      # the panel backlight off
brightnessctl -d apple-panel-bl set 50%    # back on

To blank on idle instead, run setterm --blank 1 --powerdown 2 in the text console itself (until reboot), or add consoleblank=60 to the kernel's boot options. brightnessctl -l lists the backlights; on a 13" M2 the second one (228600000.dsi.0) is likely the Touch Bar.

6. Check it from the fleet

From another machine's fleet viewer, the card should stay live with its hardware line, and a dispatch on the runner should show in its scope. On the runner, free -h shows what the desktop was holding.

Run on a 13" M2 (8 GB), 2026-10-12: step 2 (linger on; both user services survived a desktop logout), step 3 with the units above, step 4 by Tailscale SSH, and step 5 by stopping SDDM from a text console (the memory table above). Step 1 is written from the machine's default lid policy and has not been run there yet; the lid stayed open.

What does not work yet

  • radio and compaction run on the utility model, which only LM Studio can serve today (#3207).
  • Machine telemetry (CPU, memory, GPU, power) reads empty, and the residency planner sees no memory pools, until the host probe and the memory snapshot have Linux strategies.
  • A role with no tools on an unmanaged endpoint runs host-side and writes no live state, so the fleet card reads PROMPT for the whole call (#3211). Prompt-processing progress isn't shown yet either (#3210).
  • A 127.0.0.1 endpoint from inside the container. darkmux rewrites a loopback LM Studio address for the container, but not an unmanaged endpoint's URL, so a role with tools on a 127.0.0.1 endpoint dials the container itself. Use host.docker.internal in the endpoint URL (#3209).
  • darkmux doctor fails the lms binary row with no LM Studio installed, and warns on rows whose probes are macOS-only.
  • A model server that runs out of GPU memory mid-request can stop answering without closing the connection; darkmux then waits out its full timeout.
