# Environment variables and their `config.json` homes

Reference for every `DARKMUX_*` variable, what it does, and which
`config.json` field it overrides.

**You rarely need to read this.** `darkmux doctor` prints the *resolved* value
of each setting along with where it came from (env, config, or built-in
default), which answers "what is this set to right now" better than a table
can. Reach for this file when you need to know what a knob *means*, or which
config field an env var maps onto.

Precedence is the same for every setting and lives in exactly one place in the
code (`darkmux_types::config_access`):

    env(DARKMUX_*)  >  config.json  >  built-in default

The env tier is read **live per access**, so a `set_var` in a test or a
power-user `export` still wins.

## Boolean values — one vocabulary

Every boolean `DARKMUX_*` variable accepts the **same tokens**, and so does
`darkmux config set` (`darkmux_types::config_access::parse_bool_token`;
case-insensitive, surrounding whitespace trimmed):

| Reads as | Tokens |
|---|---|
| **true** | `1`, `true`, `yes`, `on` |
| **false** | `0`, `false`, `no`, `off` |

What an **unrecognized** token means depends on which way the knob fails, and
the two are deliberately different:

- **Opt-OUT knobs** (on by default — `DARKMUX_THERMAL_ENABLED`,
  `DARKMUX_THERMAL_TIER4_ENABLED`, `DARKMUX_CHECK_UPDATES`,
  `DARKMUX_FEEDBACK_INJECTION`, `DARKMUX_POWER_REFUSE_START_BELOW_MIN`,
  `DARKMUX_POWER_PAUSE_RUNNING_BELOW_MIN`) read an unrecognized token as
  **true**. A typo must never be the thing that turns off a safety behavior.
- **Opt-IN knobs** (off by default — `DARKMUX_CMD_ENABLED`,
  `DARKMUX_HOOKS_ENABLED`, `DARKMUX_STRICT_SELECTION`) read it as **false**,
  fail-closed for the same reason in reverse.

This was three separate vocabularies until #2774 (review C7, finished in
round 3). Spellings changed meaning in the process, on knobs where the new
reading is the one an operator meant — every flip is in the intent-honoring
direction, so nothing that used to disable a knob now silently enables it:

- **`off` gained its meaning** on most knobs. All but one recognized only
  `0`/`false`/`no` as false, so `off` disabled nothing.
- **Case stopped mattering.** `False`, `FALSE`, `No`, `NO`, `OFF` and every
  other casing now read as false; previously only the lowercase spellings did,
  so `OFF` left a knob ON.

Which knob each flip reaches:

| Knob | `off` gained meaning | case stopped mattering |
|---|---|---|
| `DARKMUX_THERMAL_ENABLED` | yes | yes |
| `DARKMUX_CHECK_UPDATES` | yes | yes |
| `DARKMUX_POWER_REFUSE_START_BELOW_MIN` | yes | yes |
| `DARKMUX_POWER_PAUSE_RUNNING_BELOW_MIN` | yes | yes |
| `DARKMUX_FEEDBACK_INJECTION` | no — it already accepted lowercase `off` | yes |
| `DARKMUX_THERMAL_TIER4_ENABLED` | n/a — new in #2774, no prior reading | n/a |

`darkmux doctor` shows what each resolves to.

Every `DARKMUX_*` var below is the **top tier** of `env > config.json > built-in default` — it wins live, and each maps to a `config.json` field (mapping after the table). Use env for per-shell/CI/test overrides; use `config.json` for durable operator config. Flow records carry per-record provenance fields auto-populated from these at write time. `darkmux doctor` surfaces what each resolves to.

| Variable | Default | Effect |
|---|---|---|
| `DARKMUX_MACHINE_ID` | hostname | Logical fleet name **stamped at record-write time** on every new flow record. Operator-named (`studio`, `mini-1`) reads better in the topology view than DNS-style hostnames. Pre-1.4.0 records lack the field (which the viewer renders as `unknown`). |
| `DARKMUX_FLEET_MODE` | `standalone` | The machine's declared fleet position — `standalone` (single machine), `hub` (the always-on coordinator; supervises its own Redis per #936), or `peer` (points at a hub). Operator-**declared** under `config.fleet.mode`; detection is only a doctor cross-check (declared ≠ observed), never the source of truth. `darkmux doctor` shows it with provenance and flags an unrecognized value (treated as `standalone`). Downstream fleet features key on it (#933). |
| `DARKMUX_FLOWS_DIR` | `~/.darkmux/flows` | Where the per-day JSONL files live (LocalFileSink — casual write target). |
| `DARKMUX_FINDINGS_DIR` | `<darkmux root>/findings` | (#2265) Where finding records live — one write-once `<dispatch>/<seq>/finding.json` per accepted `create_finding` call. The flow stream stays the audit trail; this directory is the queryable copy `finding list` / `finding show` read, and `finding sync` replays the stream into it. |
| `DARKMUX_MODS_DIR` | `<darkmux root>/mods` | (#2265) Where mod records live — one `<key>/mod.json` per `mod create`, plus that mod's own `attachments/`. A mod is how something COULD change: a KIT of instructions plus data, in whatever form the proposer chose, opaque to darkmux. Its key is MINTED per mod, never derived from a finding, so two agents proposing different changes for one observation produce two records rather than one overwriting the other. Read with `mod list` / `mod show`; `finding show` derives the reverse view by scanning this store. The second producer writes here too: a dispatch's accepted `create_mod` call, materialized from its emission the way a finding is (a mod whose parts were not all usable is still written, with the reason in its own `warnings`). |
| `DARKMUX_AUDIT_DIR` | unset → AuditFileSink off | When set, flow records ALSO write to a hash-chained per-day JSONL under this directory (AuditFileSink, #163). **POSIX-only** (Linux/macOS — Windows is unsupported; the env var is recognized but the sink is skipped). Cross-process safe via `flock(2)`. `darkmux flow integrity-check` walks the chain and **exits with status 2 on any chain break** so cron/CI can flag tampering; **`--strict` adds exit 3 for a file that could not be content-verified at all** (a pre-2.6.0 struct-hash file, or one whose `hash_format` header marker is missing — #1775). The two codes are deliberately distinct: `2` is evidence of divergence, `3` is absence of evidence, and an unattended consumer needs to tell them apart. Strict is opt-in because a genuine read-only pre-2.6.0 archive is not a failure — but on a fleet already writing byte-hashed files no NEW legacy file should appear, so an unexpected one is itself a signal. `darkmux doctor` rolls up the same result. A DETECTION substrate: `flow integrity-check` recomputes each chain and reports the first divergence, which catches in-place edits, reordering, insertion, and any deletion that is not a pure suffix (removing the first record or a middle run breaks the next record's `prev_hash` linkage). It does **not** catch every edit — notably **deleting records from the END of a file leaves a shorter but fully consistent chain that validates clean**, and whole-file deletion is invisible. See SECURITY.md for the full list. It does not prevent alteration, and running it does not make an operator compliant with any regulatory framework. |
| `DARKMUX_REDIS_URL` | unset → Redis off | When set, flow records also XADD to the Redis stream (coordination substrate; not the audit substrate). Combined with `DARKMUX_AUDIT_DIR` produces the full composition: `TeeSink([LocalFile, Audit, Redis])`. See [#162](https://github.com/kstrat2001/darkmux/issues/162) Phase 3. |
| `DARKMUX_REDIS_STREAM` | `darkmux:flow` | Override the Redis stream name. |
| `DARKMUX_REDIS_MAXLEN` | `10000` | Approximate retention cap for the Redis stream (`XADD MAXLEN ~ N`); `0` for unbounded. |
| `DARKMUX_INACTIVITY_TIMEOUT_SECONDS` | `600` | Per-dispatch inactivity budget. The host-side watchdog **hard-kills** the container at 100% if no proof-of-work signal lands. The runtime-side detector fires a **soft warning** at 75% (model-facing nudge to wrap up gracefully or escalate via `BLOCKED:`); both reset on the same proof-of-work signals (any tool.completed, any compaction). A productive dispatch never sees either; a stuck one gets the soft chance before the hard kill. Pathological tool patterns are caught by their dedicated detectors (cycle, cascade, edit-drift, reasoning loops) — the deadline trusts activity; the detectors catch struggle. (#457 + #464 + #466; renamed from `DARKMUX_RUNTIME_DEADLINE_SECONDS`) |
| `DARKMUX_MAX_PAUSE_MS` | `900000` (15 min) | (#2114) Ceiling on how old a `pace.json` pause instruction's `written_at_ms` heartbeat may be while still honored. `darkmux acp`/the runtime's pause/resume loop rests in bounded ≤2s increments while a host-written `pace.json` (the #2110/#2109 thermal governor/breaker, or a hand-written file) holds `pause: true`; a writer that wants the pause to keep holding just keeps RE-STAMPING `written_at_ms` on its own cadence — there is no separate "hold indefinitely" flag. Once the stamp goes stale past this ceiling (a dead or hung writer stopped re-stamping), the runtime stops honoring the pause and continues rather than resting forever, so a killed governor process can never make a dispatch immortal against its own inactivity watchdog. **No `config.json` field yet** — the governor/breaker that would own `runtime.thermal.max_pause_ms` (#2110/#2109) hasn't merged to main; until it does, this is a bare host-env pass-through (`dispatch_internal.rs`'s `max_pause_ms_env`), forwarded into the container ONLY when the host itself has it set — unset means the container falls back to its own built-in default above, not "0" or "unset forever." |
| `DARKMUX_TURN_DELAY_MS` | `0` | (#2094) Global inter-turn rest — the runtime sleeps this many milliseconds **between turns only** (never before the first turn, never after the last). A deliberate throttle, not a stall: the sleep is recorded as `rest_ms`/`rests` alongside an **unchanged** `wall_ms` (wall stays wall; a caller wanting model-only time subtracts `rest_ms` from `wall_ms` itself) — a rested run's wall clock must never be misread as a slow model. Never applied to an agentic-REMOTE dispatch (a hosted-endpoint "brain" has no local GPU on this host to rest, and honoring it would only add latency the per-execution remote token allowance pays for nothing — local seats always get it, subject to the clamp below). Clamped against `DARKMUX_INACTIVITY_TIMEOUT_SECONDS`: a configured value at or above **half** the inactivity timeout is clamped to half the timeout rather than ever honored verbatim, with a loud warning naming the clamp — a rest, plus the tailer's own polling overhead, can never itself approach the watchdog's deadline. Maps to `runtime.turn_delay_ms`; `darkmux doctor` shows the resolved value, its provenance, and whether the clamp fired. |
| `DARKMUX_HOST_SAMPLER_INTERVAL_MS` | `5000` | (#2107, #1833, #2108, #2413) The serve daemon's continuous host sampler: every N ms it reads the machine IN PROCESS — CPU tick deltas and memory pressure from mach kernel counters, per-perf-level cluster utilization and frequency plus CPU/GPU/ANE power from IOReport, thermal state from `ProcessInfo.thermalState`, GPU utilization from the `IOAccelerator` IORegistry node; zero model work, zero process spawns — into an in-memory ring of the last 10 minutes, and serves `now` + window stats (mean / p95 / max, plus power, thermal and `energy_mwh`) as `load` on `GET /machine/resources`, which the viewer's machine drawer and modal read while open. **The ring samples at this cadence unconditionally**, but flow-record EMISSION (`machine.telemetry`, machine-scoped — no session/model/mission/phase fields) is gated on machine activity: this cadence while at least one dispatch is live anywhere on the machine, 10x slower (one tenth the rate) while idle. **This is now the ONE host sampler on a machine** — a machine-scoped singleton lock (`<darkmux-home>/liveness/host-sampler.lock`) ensures exactly one emitter at a time; when no `darkmux serve` daemon runs, the first dispatch process becomes the emitter for as long as it runs (always at the base cadence, since a live dispatch is definitionally not idle), releasing the lock on exit. `telemetry.process` is RETIRED, full stop (FLOW schema 1.42.0, #2413): the per-dispatch container-loop emitter went first, and the other remaining producer — `darkmux_crew::run_obs::HostTelemetrySampler` (mission launches, ACP sessions) — was deleted in the same issue's round 2, along with the `HostTelemetrySampler`/`RunObs` types themselves, once `mission_launch.rs`, `acp_panel.rs`, and the (now-shim) review pipeline each stopped constructing one. Nothing in the current binary can produce a `telemetry.process` record; a reader may still see one from a pre-1.42.0 day file (lenient-on-read, no migration). `machine.telemetry` is the sole survivor and carries a `payload.interval_ms` field: the MEASURED gap since that producer's own previous sample, not the configured cadence, so a stalled or contended sampler is visible in the data rather than assumed on-schedule. `0` disables the sampler (and its lock) entirely. The sampler stamps its own cost per sample (`load.now.sampler_cost_ms` / `payload.sampler_cost_ms`): **measured mean 9.7 ms, max 12 ms on an M5 Max / macOS 26** (a debug build), so the default cadence spends about 0.2% of the machine on watching it. Before #2108 the same sample was four shell-outs (`top -l 1 -n 0`, `sysctl`, `vm_stat`, `ioreg`) costing ~780 ms — and `top -l 1`'s CPU line is a since-boot average, so the recorded CPU figure was wrong-ish as well as expensive. Every source degrades to null independently on a host that lacks it. Maps to `runtime.host_sampler_interval_ms`; `darkmux doctor`'s `host sampler` check shows the resolved singleton-lock state (one healthy sampler, a stale lock, or a recent second-acquisition-attempt), and its separate `host probe` check names which probe sources resolved and the measured per-sample cost. |
| `DARKMUX_THERMAL_ENABLED` | `true` | (#2110/#2109) Master gate for the thermal governor + breaker (see the next four rows). `false`/`0`/`no`/`off` (any casing) disables both — the per-dispatch host sampler still reads the OS thermal state for telemetry, but never writes the pace file or a crawl's `STOP` file. (#2454 — read side: a crawl's `crawl.unit` step checks that `STOP` file before dispatching each unit, unconditionally on file presence, same as the pace file's own reader; this gate only governs whether the breaker ever WRITES one.) On by default: this is hardware-safety behavior on the operator's own machine, not an opt-in integration, so it follows `strict_selection`/`check_updates`'s on-unless-told-otherwise convention. Maps to `runtime.thermal.enabled`; `darkmux doctor` shows the resolved knobs. |
| `DARKMUX_THERMAL_PAUSE_AT` / `DARKMUX_THERMAL_RESUME_AT` | `serious` / `fair` | (#2110) OS thermal states (`nominal`/`fair`/`serious`/`critical`) that drive the governor's hysteresis: at or above `pause_at`, the host writes `<out_dir>/pace.json` (the mounted `/darkmux-out` bookkeeping dir, NOT `/workspace` — #2114's schema) with `pause: true, reason: "thermal"` — the in-flight dispatch rests at its next turn boundary. The pause clears once the state has held at or below `resume_at` continuously for `DARKMUX_THERMAL_RESUME_HOLD_MS`. **Both are normalized at resolution** (trimmed, lowercased), so `Serious` and `serious` are the same state to every consumer (#2774 round-3 C4). **`pause_at` must be STRICTLY more severe than `resume_at`** — the two need a real band between them for the entry and resume holds to occupy. If they touch or invert (`pause_at = resume_at = fair`, say), every reading would be at once "hot enough to pause" and "cool enough to resume", so the governor **disarms its soft tiers entirely** — no duty-cycle, no pause/resume, no episode-count hold — and says so at dispatch start; the breaker (`critical`, and the sustained `cpu_speed_limit_pct` floor) is unaffected and still runs. Setting `pause_at` to `critical` has the same practical effect for a different reason: the breaker's own rule fires first on any such reading, so the soft tiers never get a turn. `darkmux doctor` warns about both shapes (#2774 round-3 MF1/C4). Map to `runtime.thermal.pause_at` / `runtime.thermal.resume_at`. |
| `DARKMUX_THERMAL_RESUME_HOLD_MS` | `60000` | (#2110) How long (ms) the state must hold at/below `pause_at`'s resume threshold, continuously, before the governor clears the pause — the hysteresis window that stops a state bouncing right at the threshold from flapping the pace file on and off. **`0` means "resume on the first recovery reading"** — no sustained hold required — the same reading `DARKMUX_THERMAL_SPEED_LIMIT_HOLD_SAMPLES` gives its own `0`. It does NOT mean "resume regardless of the reading": the transition is gated on the reading being at/below `resume_at` as well as on the hold having elapsed (#2774 round-6 MF1), so a machine that is still `serious` stays paused at every value of this knob. Also governs tier 2's duty-cycle entry and exit holds. Maps to `runtime.thermal.resume_hold_ms`. |
| `DARKMUX_THERMAL_MAX_PAUSE_MS` | `900000` | (#2110) Cap on one continuous pause episode (15 minutes by default) before the governor hands off to the breaker (`DARKMUX_THERMAL_MIN_CPU_SPEED_LIMIT_PCT` below) rather than resting indefinitely on a machine that never cools. **`0` means UNBOUNDED — never hand off to the breaker, rest as long as it takes** — darkmux's standing reading of a `0` bound (`redis.maxlen`, `runtime.step_command_timeout_seconds`, `DARKMUX_THERMAL_EPISODE_THRESHOLD`), never "instantly" (#2774 round-6 MF2). One caveat worth knowing before setting it: this knob does double duty as the runtime's pace-file STALENESS ceiling (`runtime/src/pace.rs`, forwarded as `DARKMUX_MAX_PAUSE_MS`), where a literal `0` would mean "honor a pause for 0 ms" — i.e. ignore every pause. So the unbounded reading applies to the EPISODE CAP only; the freshness window falls back to the 15-minute default. A live governor re-stamps well inside that window, so an unbounded pause still holds indefinitely — what the window bounds is a pause whose WRITER has died, which is #2114's heartbeat contract and is deliberately not opt-out-able. **Practical floor: one sampler tick (2000 ms).** A value below that is not clamped — it is nonsensical as an episode cap and darkmux does not second-guess an operator's number — but it does not do anything useful either: the host writes `pause: true` and re-stamps on its own cadence while telling the container to expire anything older than, say, 1 ms, so `is_expired` is true on essentially every poll and the runtime keeps working through a pause the host believes it is holding. Set it to `0` (unbounded) or to at least a few sampler ticks. Maps to `runtime.thermal.max_pause_ms`. |
| `DARKMUX_THERMAL_MIN_CPU_SPEED_LIMIT_PCT` | `50` | (#2109) Breaker floor: `cpu_speed_limit_pct` (from `IOPMCopyCPUPowerStatus`) held below this for `DARKMUX_THERMAL_SPEED_LIMIT_HOLD_SAMPLES` consecutive samples — or the OS thermal state reaching `critical` (immediate, no hold) — pauses the pace file with `reason: "thermal-critical"` AND, for a crawl mission, drops the crawl's `STOP` file. **(#2454)** `crawl.unit`'s own step kind reads that file (via `thermal_governor::stop_file_path_from_record_context`, never a raw re-join — #2157) before it prepares each unit's dispatch, so no further unit actually gets dispatched: the crawl's summary reports `stopped_by: "thermal"` and each skipped unit's own outcome as `thermal_stop`, named rather than folded into `error`. The STOP file is scoped to the RUN that wrote it: the breaker stamps its own mission id into it and a unit honors it only when it names that unit's mission, because **nothing ever removes this file** and its path is keyed to the workspace — an unscoped one would refuse every future crawl on that workspace forever from a single thermal event. A STOP file naming no mission (hand-written, or from a build older than #2454) is honored by every mission until a human removes it, and the skip message names the exact `rm`. (Known gap: a crawl spec with an explicit `root:` override cannot be reconstructed from `record_context` alone, so this STOP file is neither written nor read for that case — symmetric, so such a crawl gets no breaker rather than a half-working one.) Never kills the container; the in-flight unit pauses at its next turn boundary with its checkpoint persisted (#2114). Resume is the operator's call once #2114's `--resume` CLI flag ships (not wired yet) — the breaker does not un-pause itself on recovery. `0` disables this signal outright — the comparison is `pct < floor` and no reading is below zero — leaving the `critical`-state check as the only breaker trigger; that is the honest reading of "no floor", and it is why this knob is not clamped. **Ceiling: 100.** `cpu_speed_limit_pct` is a percentage, and `100` is what the probe reports when no cap is recorded at all, so a floor ABOVE 100 is satisfied by every reading a healthy machine produces: the breaker trips on the `DARKMUX_THERMAL_SPEED_LIMIT_HOLD_SAMPLES`'th sample of EVERY dispatch and drops a `thermal-critical` STOP file on a cold machine. Not clamped, for the same reason `0` is not — but `darkmux doctor` warns above 100 and names what it will do (#2774). Maps to `runtime.thermal.min_cpu_speed_limit_pct`. |
| `DARKMUX_THERMAL_SPEED_LIMIT_HOLD_SAMPLES` | `3` | (#2110/#2109 review finding 7) Consecutive samples `cpu_speed_limit_pct` must read below the floor before the breaker trips on that signal — a lone low sample is common DVFS noise, not a sustained condition. Does NOT apply to the `critical` state check above, which still trips on the first sample. Clamped to a minimum of 1 (`0` is coerced, not "disabled" — `darkmux doctor` warns). Maps to `runtime.thermal.speed_limit_hold_samples`. |
| `DARKMUX_THERMAL_DUTY_DELAY_MS` | `15000` | (#2774 tier 2) Base per-turn delay (ms) the host instructs the runtime to rest for while the machine sits in the `fair` band — at or above `resume_at` but below `pause_at`, held continuously for `DARKMUX_THERMAL_RESUME_HOLD_MS`. Written into `<out_dir>/pace.json` as `pause: false, turn_delay_ms: <n>`, so the run keeps working at a lower duty cycle rather than stopping: this is a PACING instruction, not a pause, and the battery governor is free to act while it holds (#2774 review F1). The delay goes through the runtime's existing inter-turn-rest budget clamp (`DARKMUX_TURN_DELAY_MS`'s own ceiling, half the inactivity budget), so a large value cannot rest a turn past the inactivity watchdog. `0` means no delay — tier 2 still tracks entry and exit, it just instructs no rest, which is the coherent reading of "duty-cycle at full speed". Maps to `runtime.thermal.duty_delay_ms`. |
| `DARKMUX_THERMAL_RATCHET_FACTOR` | `2` | (#2774 tier 3) Multiplier applied to the LIVE duty-cycle delay on every recovery from a `serious` pause — one-way, never lowered. So a run that has been through two `serious` episodes duty-cycles at `duty_delay_ms * factor^2`. `1` holds the delay steady (an explicit opt-out of the ratchet); `0` is floored to `1` rather than zeroing the delay. The live value is carried across every dispatch of the SAME crawl mission, not reset per unit (#2774 review F5). Maps to `runtime.thermal.ratchet_factor`. |
| `DARKMUX_THERMAL_EPISODE_THRESHOLD` | `2` | (#2774 tier 4) How many `serious` EPISODES a run tolerates before the Nth escalates from an ordinary pause to a terminal, operator-gated hold (`reason: "thermal-episode-limit"`) that never clears on its own. An episode is a TRANSITION into `serious`, never a sample — a hundred consecutive `serious` readings are one episode. `0` means unbounded (never escalate). Counted per MISSION, not per dispatch. Maps to `runtime.thermal.episode_threshold`. |
| `DARKMUX_THERMAL_TIER4_ENABLED` | `true` | (#2774 tier 4) Whether the episode-count escalation above is active at all. `false` makes every episode an ordinary pause/resume regardless of `DARKMUX_THERMAL_EPISODE_THRESHOLD`; the count is still recorded in the run's artifact. Accepts `true/false`, `1/0`, `yes/no`, `on/off` — the same vocabulary `darkmux config set` takes (#2774 review C7); an unrecognized token reads as `true`, so a typo can never be the thing that disables a safety tier. Maps to `runtime.thermal.tier4_enabled`. |
| `DARKMUX_POWER_MIN_BATTERY_PCT` | `50` | (#2706) The battery-charge FLOOR, in percent. A new run refuses to start below it (`DARKMUX_POWER_REFUSE_START_BELOW_MIN`) and a run already in flight pauses when charge crosses it (`DARKMUX_POWER_PAUSE_RUNNING_BELOW_MIN`). **Exactly at the floor is acceptable** — a minimum of 50 means 50 starts, 49 does not — and the same boundary governs both the refusal and the resume, so one number means one thing on every surface. Read from the in-process `AppleSmartBattery` IORegistry node (#2705), never `pmset`. **A machine with NO battery is never gated by any of this** — not "treated as 0%", not "treated as 100%": an absent reading is `None` all the way down and every entry point returns its inert answer before reading config at all. That matters concretely in a mixed fleet where the always-on hub is a desktop and the battery-bearing laptop is the inference peer; misreading absence would either block the hub permanently or silently disable the gate on the one machine it protects. Clamped to `0..=100` at resolution (a configured `250` reads as 100, per the lenient-read contract — semantic validation at resolution, never a parse failure that bricks the whole config); a `0` is meaningful and NOT coerced, being the numeric way to disable the floor without touching either boolean. Maps to `power.min_battery_pct`. |
| `DARKMUX_POWER_REFUSE_START_BELOW_MIN` | `true` | (#2706) The START policy: a mission/crawl pre-flight refuses to launch below the floor. `false` allows runs under the threshold. The refusal names what was OBSERVED, the floor, and the config field that produced the decision — darkmux enforces a threshold **the operator wrote** and never invents one, so it reports the two numbers and says where they came from rather than claiming the battery is unhealthy or recommending a charge policy. `--force` starts anyway on the launch surfaces that accept it, exactly as it does past the thermal refusal on the same pre-flight. Deliberately a SEPARATE item from the in-flight policy below: refusing to start and interrupting work in progress are different decisions with different costs, and an operator may reasonably want one without the other. Maps to `power.refuse_start_below_min`. |
| `DARKMUX_POWER_PAUSE_RUNNING_BELOW_MIN` | `true` | (#2706) The IN-FLIGHT policy: a run already going PAUSES when charge crosses the floor, and resumes when charge returns to at-or-above it. `false` lets it run to completion. **Pausing means pausing** — it writes the same `<out_dir>/pace.json` the thermal governor uses, with `reason: "battery"`, so the runtime rests at its next turn boundary in bounded ≤2s increments with its whole conversation in memory and continues from exactly there; nothing is killed and no `STOP` file is written. The pause is a HEARTBEAT, not a standing instruction (#2114): the governor re-stamps it for as long as it holds, and a governor that stopped would see the runtime release the pause once the stamp aged past `DARKMUX_THERMAL_MAX_PAUSE_MS` — which is the runtime's ceiling for EVERY pause reason, not just thermal ones. When both governors want the file, **thermal wins for a GENUINE pause** — the battery governor stands down only while thermal is actually paused/held (not merely tier 2's duty-cycling, #2774) and re-asserts on the first free tick (~2s). **Payload predicates (#1959).** A `hooks.rules[].match` entry can go past the top-level fields (`action`/`session_id`/`mission_id`/`machine_id`/`category`/`level`) into a record's own `payload`, via one or more `"payload.<dotted path>"` keys — each an exact match against a JSON scalar, AND'd with each other and with every other field on the same `match`. A key the record's payload doesn't carry (missing, or the payload isn't even an object) never matches — there's no "absent means match" reading. This is how an external tracker subscribes to a SPECIFIC shape of tool call rather than an entire `action` glob. Example — every ACCEPTED `create_finding` call, whichever mission emitted it:

```json
{
  "hooks": {
    "enabled": true,
    "rules": [
      {
        "match": {
          "action": "dispatch.tool",
          "payload.tool_name": "create_finding",
          "payload.ok": true
        },
        "http": "http://127.0.0.1:8790/events"
      }
    ]
  }
}
```

A rejected citation (a wrong line number, an unresolvable path, a budget already spent) is a FAILED tool call — `create_finding`'s own reply text (`REJECTED: …` / `NOT RECORDED — …`) is classified by the runtime the same way any other tool's failure is, so `payload.ok` is `false` for it and the rule above never fires on it. The record's `payload.context` (present only when the dispatching caller — e.g. the crawl launcher — set `DispatchOpts::record_context`) carries provenance the tool call itself can't know: `workspace`, `source`, `sha`, `rule`, `unit`.
